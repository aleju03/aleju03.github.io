# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The npm scripts are in `package.json`; `npx tsc -b` typechecks without building.

There is no frontend test suite; verification is typecheck + lint + build, then driving the affected flow in the dev server. The chat server has a smoke test: `cd server && npm test` (plain `node test/smoke.mjs`). `server/` runs with `npm start` and refuses to boot without `ADMIN_TOKEN` set.

`scripts/osu-chart.py` regenerates Rhythm Keys charts from osu!mania beatmaps (needs ffmpeg for non-mp3 audio).

## What lives here

Three independent packages:

- **Root**: the portfolio SPA (React 19 + TypeScript + Vite + Tailwind v4 + Three.js). Deployed to GitHub Pages by `.github/workflows/deploy.yml` on push to main; `VITE_CHAT_URL` comes from a repo variable and, when unset, chat features degrade to email fallbacks (`.env.example`). The `404.html` copy is the SPA-route fallback for Pages.
- **`server/`**: the AlejOS chat/arcade WebSocket server (Node 22 ESM, `ws` + `better-sqlite3`, no build step), **the shared world's presence relay**, **and the site's analytics backend** (`@aleju03/peeko` over `@libsql/client`, in its own Turso database, never `chat.db`). Deployed separately to a VPS; the JSON protocol is sketched in `server/README.md`. Deploy server and frontend together; the protocol has no version negotiation.
- **`npx-card/`**: the `npx aleju` terminal business card, published to npm by hand.

## Architecture

### Routing and versions

There is no router library. `App.tsx`'s `VersionRouter` reads `location.pathname` + pushState, re-syncing on `popstate` and the custom `NAVIGATE_EVENT`. The site ships two renderings of the same content: **full** (interactive playground, the default) and **simple** (quiet résumé, also reached via `/projects/<slug>` deep links). Initial pick: `?v=` param → localStorage → full.

The three OS routes are ordered by what they cost to load, and that ordering is the point: most visitors come for the desktop, and they should not wait on a procedural planet they may never look at:

- `/pc` boots the OS *alone*, with no portfolio page behind it and no CrtScene, so the route loads no three.js at all; it powers off via the `onPowerOff` prop, which re-syncs the router into the real site.
- `/alejOS` boots the full site straight into the OS, on the CRT, **in the room and nothing past it**: the house, its furniture and the sky out of its windows, but not the open world. You can stand up and walk the house for free; opening the front door streams the planet in behind the boot cover, once. That is `outsideWorld.ts`'s `attachWorld` plus CrtScene's `ensureWorld`/`loadWorldCovered`.
- `/world` is the far end: everything loaded up front, machine already dark, no POST/boot/login, CrtScene skipping both its intro flight and the stand-up glide and opening the lens already standing (the glide's old start was nose-to-glass on a dark tube, which is all a visitor saw while the first ring streamed). It was called `/room` until the room and the world became separable; `LEGACY_WORLD_PATH` keeps old links working and normalises them with `replaceState`.

All of them are declared in `src/version.ts` (`OS_PATH`/`PC_PATH`/`WORLD_PATH`, `isOsPath`/`isPcPath`/`isWorldPath`), which also documents the recipe for adding a version (id + `versions.<id>` copy in both languages + a branch in VersionRouter).

Far-apart components talk through window-level custom events declared in `src/events.ts` (open palette/terminal/chooser, boot the OS, OS scene ready), with no prop drilling and no global store. Overlay/scroll-lock bookkeeping is `src/overlay.ts`; theme (wipe transition) is `src/theme.ts`; en/es strings live in the dictionaries in `src/i18n.tsx`, and every user-facing string needs both.

### The full site's layer cake

Everything heavy is lazy and event-triggered, and Three.js is deliberately isolated behind those lazy chunks (see `chunkSizeWarningLimit` note in `vite.config.ts`):

1. `FullPortfolio`: the page itself. Hero name is `BlockName` (draggable 3D letter blocks + a WASD-flyable paper plane sharing one canvas); `Terminal` mounts on Ctrl+`.
2. `AlejOS` (`src/components/os/`): the portfolio as an early-2000s desktop, booted from the palette, the terminal, the paper plane being swallowed, or visiting `/alejOS`. It renders either on the 3D CRT or in a flat DOM bezel; a boot carrying `{ flat: true }` (the palette's "without the 3D", the terminal's `pc`/`boot flat`, or the `/pc` route) forces the bezel and keeps the whole 3D layer unloaded, while small/touch/reduced-motion devices fall back to it on their own. The desktop is a virtual filesystem (`fs.ts`); apps register in `apps.tsx`/`appWindows.tsx`; `osYear.ts`, `wallpapers.ts` and `sounds.ts` are small subscribable stores. Login/chat/arcade talk to `server/` over one WebSocket.
3. `warp.ts`: the 2D-canvas wormhole between the page and the OS. It opens on the hero wreck's glass (position provided by `BlockName` via `provideWarpOrigin`) and holds until the far side announces its first frame on `OS_SCENE_READY_EVENT`.
4. `CrtScene.tsx` is the presentation shell of the 3D world: renderer, screen glass, camera cinematics, light rig, HUD. The live AlejOS DOM stays interactive on the CRT via a CSS3D renderer sharing the WebGL camera; the glass mesh punches a hole through the canvas with a no-blending near-transparent material. While the camera is parked on the screen **nothing 3D renders at all**. Its `walkTick` is a thin per-frame conductor over the game runtime.
5. `src/game/`: the React-free game runtime (see `src/game/README.md` for the map and the how-to-add-things guide). Input, FPS movement + collision + swimming, the Level system (the 'overworld' and the 'backrooms' easter egg, plus the noclip cut between them), the player body, and the deterministic-procgen core (`core/rand.ts`, `core/textures.ts`).
6. `src/game/world/` is **the open world**: an endless, chunk-streamed procedural planet with Earth-like biomes, water and walkable cities, and `src/game/vehicles/` is **the fleet**: a car, a boat and a helicopter, one per medium. Both are session-scoped detail; the rules that bite live in `src/game/CLAUDE.md`, which loads whenever you work in the runtime, and the long form is `README.md`'s "The open world" and "The fleet" sections.

7. `src/game/net/` + `components/os/worldNet.ts` + `components/os/proximityVoice.ts` are **multiplayer**: the walk is shared, and so is the fleet. Nothing about the planet travels (it is a pure function of coordinates on both ends), so the wire carries only a roster, a ~15Hz snapshot of everyone's pose, chat, a WebRTC handshake, and the one thing that genuinely is not recomputable: the three vehicle transforms and the six seats. The roster's two identity fields are a name and a look. `src/game/player/look.ts` packs four colours into 24 hex characters the server relays without parsing, and the name is the chat server's own `nick`, because one socket carries one identity and the plate over your head, the chat rail and the arcade boards have to agree. Both are edited in the left column of the pause screen (`components/os/WorldIdentity.tsx`), whose preview is the real `buildPlayerBody()` rig in its own small renderer, mounted on the first pause of a session and hidden rather than unmounted afterwards, so that second WebGL context is created once instead of on every press of escape. Each machine takes two people, the server arbitrates the chairs (the one question two clients cannot settle between themselves) and relays the driver's transform to everyone else, who place it rather than integrate it. The split follows the runtime's rule: the store, the interpolation and the remote bodies are in `src/game/net/` and stay headless-safe; the socket and the voice mesh live on the React side because they reach for `import.meta.env`, a DOM WebSocket and `getUserMedia`. Playback deliberately runs two server ticks behind and interpolates, because extrapolating drags a stopping player's planted feet across the ground. Voice is a peer-to-peer mesh spatialized with `PannerNode`s, and **no audio ever touches the VPS**, which is also why there is no TURN relay and some strict-NAT visitors will not connect. `src/game/README.md`'s "Multiplayer" section is the guide.

### The scroll spine

The full site is choreographed as one continuous flight, and the thing that makes that cheap is that **`BlockName`'s canvas was already a document-pinned 3D world**, fixed to the viewport, camera riding `-scrollY * view.wpp`, spanning hero to footer. The spine fills it rather than adding a second renderer.

- `src/scroll/stations.ts`: the registry. A section opts into the flight by marking an element `data-station="work"`; adding a stop is one attribute. Everything downstream (the curve, the waypoints, the `enter`/`draw` cues) keys off this one definition of where a chapter is. Re-measures on resize, on `ResizeObserver`, and after `document.fonts.ready`, because the display face swapping in relays every heading and everything under it.
- `src/scroll/progress.ts`: one rAF driver for every scroll consumer, not a `scroll` listener each. **Nothing hijacks scrolling**: the page scrolls natively so anchors, keyboard paging, `scroll-mt-16` and the paper plane's own `window.scrollTo` follow all keep working; what is smoothed is the *response*. `BlockName` smooths inline with the shared `approach()` rather than paying for a second loop.
- `src/scroll/flightPath.ts` + `paper.ts`: the contrail itself, mounted into `BlockName`'s existing `scene`, laid out in document pixels with the same pinning math as `holder`. One `InstancedMesh` of stadium dashes generated in curve order, so the scroll reveal is `mesh.count = front * total`, with no per-frame geometry work. It borrows the letters' materials, so the theme fade reaches it without a second observer.

Two things bite here. **That canvas paints ABOVE the page content below the hero** (it is a `z-10` fixed layer declared inside the first section, the same reason the paper plane flies in front of the project mockups), so the path routes down the gutters beside the text column and only crosses it in the whitespace between sections; on narrow viewports the lane collapses to the edge and the ink thins. And **scroll velocity is a physical force to its consumers** (the tube's vertical hold slips on it, the marquee is dragged by it), so `progress.ts` clamps it to `MAX_VELOCITY`. Unclamped, an anchor jump reports ~76,000 px/s, which is not a big number, it is every consumer pinned at its limit for a second.

`components/Machine.tsx` is the act the spine ends on: a ~200vh runway with a `sticky` stage where the CRT stands up and lights its tube. Two gotchas it exists to document. A **sticky** stage's document position moves every frame, which `layoutWreck`'s `rect.top + scrollY` cannot express, so the wreck is re-pinned per frame while the act is in view. And a heading inside a pinned stage holds a constant viewport rect, so `SectionHeading` self-scrubbing degenerates to a frozen value and the characters never leave their masks. Pass `progress` in from the runway instead.

`components/phosphor.ts` is the picture on that tube: a plane parked on the wreck's glass **inside BlockName's scene**, carrying a ShaderMaterial that samples a rasterized canvas of terminal text through a magnetic displacement field, so hovering the glass bends the beam the way a speaker held against a CRT used to. It is mounted where the model is built, not where the section is; `machineProgress` drives its `uLit` (the raster paints itself down the tube as the wreck rises) and trips one degauss ring the moment it lights. Five things it exists to document. **A black rectangle is not a screen**: this began as a full-bleed band across the document running the same shader, and it read as a black band no matter what was drawn on it. A screen reads as a screen because it is bolted into a computer, on a desk, at an angle, with a bezel. **The model's UVs are not ours to trust**, so the picture is a plane raycast onto the tube face with clean 0..1 coordinates (the recipe CrtScene already used to place a cursor quad), inset to ~0.96 of the glass because any margin reads as a coloured frame rather than as bezel. The field is **aspect-corrected**, so distances are `(uv - magnet) * vec2(aspect, 1)` or a round magnet is an ellipse. The magnet's strength is a **spring, not a lerp**, because releasing has to overshoot and ring down; that is the difference between a warp filter and an object. And the copy on it holds a **twenty-column grid**: the screen is ~150 CSS px wide on the page, so type is sized off the grid rather than picked, and a longer status list renders as green noise.

### Sound

`src/audio/`: Howler owns playback, the pool, fades, mute state and the mobile unlock; **it is fed object URLs rendered at runtime, so no audio ships**. `synth.ts` builds each cue in an `OfflineAudioContext` from the same soft sine/triangle voice as `os/sounds.ts` and encodes 16-bit WAV; `bank.ts` is the cue table; `index.ts` is the bus; `wire.ts` attaches it to the `events.ts` spine the way `analytics.ts` does, so the palette, terminal, chooser, navigation and every route into the OS are scored with no `cue(...)` call sites in those components.

Rules that are quiet to get right and loud to get wrong. Both Howler and the bank load **lazily on the first gesture**, since browsers refuse audio before one anyway. **Reduced motion means silence**, full stop. Nothing plays **while AlejOS covers the page**, because the OS has its own synthesized voice, and `cue()` checks that itself rather than trusting call sites. **There is no ambient bed and there should not be one**: there was, five seamlessly-looping E minor pads, and a sustained minor drone under a page reads as a corridor you cannot get out of rather than as atmosphere. The score's job is to make the page feel responsive to a stranger deciding whether to keep reading, so it is silence until they touch something.

**Loudness is declared, not hand-gained.** Each cue in `bank.ts` names a target peak and `renderCue` normalises the rendered buffer onto it, so the gains inside a cue are only its internal balance. That split exists because the two were once the same numbers, every cue was written to "quiet", and the whole bank measured -22 to -31 dBFS at the master bus, which is inaudible on laptop speakers. Do not try to fix a level with `MASTER`: Howler clamps its global volume to 1, so there is no headroom above it, and it is there for two cues landing on one frame. Measure at the bus (an AnalyserNode on `Howler.masterGain` in headless Chrome) rather than trusting the numbers in the source.

### Analytics

Traffic is counted by [peeko](https://github.com/aleju03/peeko), my own self-hosted analytics core, wired up in three pieces:

- `src/analytics.ts`: capture. Derives its endpoint from `VITE_CHAT_URL` (so there is no second env var), queues events and posts them in one batch, `sendBeacon` on hide. It subscribes to the `events.ts` spine, so the palette, terminal, chooser, navigation and every route into the OS are instrumented with **no call sites in those components**. Add new site-wide instrumentation there first. Explicit `track()` calls exist only where the event has no window event behind it (project opened, contact clicked, app opened, login).
- `server/src/analytics.js`: the store. Capture is a public, origin-checked, rate-limited HTTP route; every **read** is admin-only and travels over the already-authenticated chat WebSocket, so no dashboard token ever reaches a browser. peeko's own `/monitor` and `/live` routes are deliberately not mounted.
- `src/components/os/PeekoApp.tsx` + `peeko.ts`: the dashboard, an AlejOS app that only appears in the admin's Start menu. Hiding it is presentation; the server refusing the reads is the actual gate.

Scroll depth (one event per quarter, once each), `sound_toggle` and `sheet_torn` ride the same spine; the depth subscription is skipped on the OS routes, which have no page to scroll. Anything beyond peeko's extracted columns rides in the props bag and is read back with `getBreakdown`, so new custom events need no server change. `src/game/` stays out of this, because the runtime must keep running headless, so instrument from the React side (`CrtScene`), never from inside the sim.

### Data is the single source of truth

`src/data/projects.ts` / `experience.ts` / `skills.ts` drive the React pages **and** `/llms.txt`, which a Vite plugin in `vite.config.ts` generates from the same modules so the plain-text rendering can't go stale. Content edits go in the data modules, not components.

## Conventions that matter

- **Nothing shipped, nothing copyrighted**: sounds are synthesized with WebAudio (`sounds.ts`, `audio/synth.ts`, `game/levels/backrooms.ts`). The portfolio page's score goes through Howler, but as runtime-rendered WAV blobs, never files. Textures are drawn onto canvases at runtime (`canvasTexture` in `src/game/core/textures.ts`). Keep new assets procedural. Two exceptions, both CC and both credited in a `LICENSE.md` beside the files, and additions there must be too: the GLB models in `public/os/models/`, and the three house-door clips in `public/os/sfx/` (`game/core/sfx.ts`, which still keeps a synthesized voice per clip as its cold-load fallback). A recorded one-shot must be peak-matched against the synthesized sounds before it ships; normalized clips run ~4x hotter than this mix. Some of the world's GLSL (the sky's FBM clouds, the water's Voronoi cel highlights, the grass recipe) is adapted from `cortiz2894/stylized-components` (MIT © Christian Ortiz), credited in the module headers where it lives. Keep those notices when moving the code.
- **3D performance idioms** (the target is *tiered*: `src/game/world/quality.ts` classifies the GPU before any level builds; discrete cards get a wider grass field, fuller canopies and a 2048 sun shadow map; integrated/mobile/software renderers get the lean tier everything was first tuned on, with CrtScene's adaptive pixel-ratio governor under both. Add new density/budget knobs to the tier record, not as new constants; what the *visitor* sets is separate, in `components/os/roamPrefs.ts`, and includes a frame limiter defaulting to 160 — `walkTick` drops whole ticks against a carried deadline rather than only skipping the render, and the governor's frame budget has to clear that limiter's interval or a low cap reads as a card that cannot cope): house shadow maps are hand-baked (`shadow.autoUpdate = false`, flagged with `needsUpdate` only near a moving caster, with the cold one-light-per-frame bake completed under `BootCover`); the sun also keeps `castShadow` and `shadow.autoUpdate = false` stable, fades strength through a uniform indoors/at night, and refreshes its moving map after meaningful travel or solar rotation. Static scene graphs get `matrixAutoUpdate = false` after one `updateMatrixWorld(true)`, and anything that must keep moving opts out via `userData.dynamic`; geometry is merged/instanced per chunk; the house-model download overlaps the first shader compile, but attachment and model-dependent compilation finish under `BootCover` so no new variant lands mid-walk. The open world adds two more: chunk building is queued and time-boxed (`streamer.ts`'s `BUDGET_MS`) so a border crossing never costs a frame, and stylized shading is done by `onBeforeCompile` injection into standard materials rather than hand-written shaders, which keeps the scene's fog, tone mapping and lighting instead of reimplementing them. Follow these patterns when touching the scene or the frame loop pays for it.
- **The room and the open world load separately, and the seam is `outsideWorld.ts`.** `buildOutsideWorld` is eager and puts up the sky, a fog-bound placeholder ground and nothing else; `attachWorld()` dynamically imports `src/game/world/*` and swaps in the real terrain, and CrtScene's `ensureWorld()` does the same for `vehicles/registry` (the null object in `vehicles/emptyFleet.ts` holds the binding until then, so the ~35 fleet call sites, several of them in the hot tick, need no guards). Measured: `/alejOS` went from 11.4 s to 4.1 s to first frame and from 136 linked programs to 45, and CrtScene's chunk from 120 kB gzip to 56 kB. Two traps when touching this. **Anything world-shaped must be read through a live closure, never snapshotted**. `homeLevels`' overworld takes `waterY` as a *getter* because the level object is built on the first frame, when there is no sea. And **`bakeShadowsCovered` does not bake the sun**: its only guaranteed bake was a side effect of `warmForRoam`, so gating that on the world left an ordinary boot with a shadowless sun, which does not read as "no shadows": `sky.ts` damps indoor ambience assuming the shell casts, so the whole room rendered as a flat blue-grey void. `bakeSunCovered()` now runs on every 3D boot.
- **Most of a cold boot is the driver linking shaders, not anything this repo does.** Profiled on a discrete card, the `/room` boot spent ~4.6 s inside three's `WebGLUniforms`, reached from `setProgram → getUniforms → onFirstUse`, which is the *first draw* of a material blocking until its link finishes, and halves on the next load once the browser has the programs cached. Two consequences worth keeping. **Nothing may be left to link mid-walk**: toggling the sun's `castShadow` at the indoor or night threshold changed the shader configuration and used to link every depth-capable surface variant in one frame, measured at 2.8 s. That flag is now invariant, and `warmForRoam` pays the real depth draw during boot at the actual front-door position. The car's two headlights likewise change `NUM_SPOT_LIGHTS` when they appear at dusk, so `setLightWarmup(true)` exposes them at zero intensity for a covered compile and first draw before restoring their live visibility. And **forcing first draws is a bad trade *outdoors* and the right one indoors.** A four-heading sweep to warm every chunk cost nearly four seconds to avoid a hitch worth a tenth of one; the world is too big to pre-draw and the fog hides what streams in anyway. The room is the opposite case, because **every lens into this scene opens facing the computer** (`/world` stands there, an ordinary boot flies the intro into the glass and parks), so the furnished house behind the camera has never crossed a frustum, and `compileAsync` covers neither `onFirstUse` nor geometry buffer uploads. Measured on an RTX 4070: standing up and turning round cost five frames of 123-137 ms carrying **897 `bufferData` calls and 5 program links**, against a locked 16.7 ms everywhere else. `warmRoomDraw` pays that in one 1px render with **frustum culling switched off for the pass**, so a single submit touches every mesh in the room and no heading is left cold. Outdoor drawables stay hidden throughout, because without occlusion culling an unculled world would submit the whole planet through the back wall, which is what the old sweep lost on. **Where** it runs is the other half: `/world` pre-pays it under BootCover because it opens standing and can turn immediately, while an ordinary boot schedules it on `requestIdleCallback` the moment the intro parks, since that route ends on a live-DOM screen with the 3D layer rendering nothing and a login form in front of the visitor, so the warm-up is free there and must stay off a critical path that took `/alejOS` from 11.4 s to 4.1 s. Measure before moving a cost around; wrapping `linkProgram` (or reading `info.programs.length`) before and after an action tells you whether a stall is linking, and wrapping `bufferData` tells you when it is a first draw instead.
- **Anything covering a load must animate on the compositor.** `BootCover.tsx` is over a main thread that is blocked in multi-second lumps, so its bar is a `transform: scaleX` transition and its sweep is a `translateX` keyframe. `warp.ts` follows the same rule: canvas draws the entry and exit, but a pre-promoted transform/opacity-only DOM tunnel owns the covered ride while AlejOS and the room load. A rAF loop, a React counter or an animated `width` all freeze solid for exactly the part of the wait they exist to cover.
- **Module-header prose comments**: nearly every nontrivial module opens with a paragraph explaining what it owns and why it's shaped that way (see `game/levels/houseWorld.ts`, `warp.ts`, `CrtScene.tsx`). Keep them accurate when changing behavior, and write one for any new module.
- Walk-mode collision is a flat `THREE.Box3[]` (`game/physics/collision.ts`), height-aware: a box blocks only where it overlaps the body, so a low enough top is a floor you climb (`supportY`) rather than a wall. Solids must register a box or the player walks through them (the backrooms entrance works by deliberately not registering one), **and must be marked `noStand()` unless their box top is somewhere a player could stand**. Walls, fences, lamp poles and canopies are taller than the things they wrap, and the climbable furniture below them otherwise chains into a ladder onto the wall tops. Each level owns its CollisionSet; new areas implement the `Level` contract in `game/levels/types.ts`. Ground height is `Level.groundYAt(x, z)` where a level has terrain, and a flat `groundY` where it doesn't; a level with a `waterY` swims when the water is over the chest. The one exception to the box is a solid that *rotates*: an AABB around a 9.4-unit car parked at 45° is 9.5 units wide, and you meet it two units off the paint. Those carry a `hull`: an oriented profile of stations (half-width and standable height per local z, blended linearly) that the box then merely bounds as a broad phase. Only the vehicles have one, and their tables are mapped off the same `SECTIONS` the bodywork is lofted from; everything the world builds is axis-aligned by construction and pays nothing for the feature.
- **The camera's far plane must clear the sky dome's radius outright.** A far plane is a plane; a dome centred on the camera is a sphere, so everything within `acos(far / radius)` of the view axis is clipped. At `far = 400` against a 430 dome that was a hard-edged forty-degree disc of empty background pinned to the middle of the screen, sliding over the stars as you turned. It looks like a texture bug and it is a frustum bug.
- **The game runtime stays React-free and renderer-optional**: `src/game/` must keep running headless. That is what let the multiplayer store and the remote bodies be driven and asserted on in Node, and the long-term plan is still this sim running authoritatively there. React components render and orchestrate; they don't own game state.
