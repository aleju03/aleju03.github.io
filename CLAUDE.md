# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The npm scripts are in `package.json`; `npx tsc -b` typechecks without building.

There is no frontend test suite; verification is typecheck + lint + build, then driving the affected flow in the dev server. The chat server has a smoke test: `cd server && npm test` (plain `node test/smoke.mjs`). `server/` runs with `npm start` and refuses to boot without `ADMIN_TOKEN` set.

`scripts/osu-chart.py` regenerates Rhythm Keys charts from osu!mania beatmaps (needs ffmpeg for non-mp3 audio).

## What lives here

Three independent packages:

- **Root** — the portfolio SPA (React 19 + TypeScript + Vite + Tailwind v4 + Three.js). Deployed to GitHub Pages by `.github/workflows/deploy.yml` on push to main; `VITE_CHAT_URL` comes from a repo variable and, when unset, chat features degrade to email fallbacks (`.env.example`). The `404.html` copy is the SPA-route fallback for Pages.
- **`server/`** — the AlejOS chat/arcade WebSocket server (Node 22 ESM, `ws` + `better-sqlite3`, no build step), **the shared world's presence relay**, **and the site's analytics backend** (`@aleju03/peeko` over `@libsql/client`, in its own Turso database — never `chat.db`). Deployed separately to a VPS; the JSON protocol is sketched in `server/README.md`. Deploy server and frontend together — the protocol has no version negotiation.
- **`npx-card/`** — the `npx aleju` terminal business card, published to npm by hand.

## Architecture

### Routing and versions

There is no router library. `App.tsx`'s `VersionRouter` reads `location.pathname` + pushState, re-syncing on `popstate` and the custom `NAVIGATE_EVENT`. The site ships two renderings of the same content: **full** (interactive playground, the default) and **simple** (quiet résumé, also reached via `/projects/<slug>` deep links). Initial pick: `?v=` param → localStorage → full. `/alejOS` always boots the full site straight into the OS. `/pc` boots the OS *alone* — no portfolio page behind it and no CrtScene, so the route loads no three.js at all; it powers off via the `onPowerOff` prop, which re-syncs the router into the real site. `/room` is `/pc`'s mirror image: the site behind it as usual, but the session starts at the far end — machine already dark, no POST/boot/login, CrtScene skipping both its intro flight and the stand-up glide and opening the lens already standing (the glide's old start was nose-to-glass on a dark tube, which is all a visitor saw while the first ring streamed). All three OS routes are declared in `src/version.ts` (`OS_PATH`/`PC_PATH`/`ROOM_PATH`, `isOsPath`/`isPcPath`/`isRoomPath`), which also documents the recipe for adding a version (id + `versions.<id>` copy in both languages + a branch in VersionRouter).

Far-apart components talk through window-level custom events declared in `src/events.ts` (open palette/terminal/chooser, boot the OS, OS scene ready) — no prop drilling, no global store. Overlay/scroll-lock bookkeeping is `src/overlay.ts`; theme (wipe transition) is `src/theme.ts`; en/es strings live in the dictionaries in `src/i18n.tsx` — every user-facing string needs both.

### The full site's layer cake

Everything heavy is lazy and event-triggered, and Three.js is deliberately isolated behind those lazy chunks (see `chunkSizeWarningLimit` note in `vite.config.ts`):

1. `FullPortfolio` — the page itself. Hero name is `BlockName` (draggable 3D letter blocks + a WASD-flyable paper plane sharing one canvas); `Terminal` mounts on Ctrl+`.
2. `AlejOS` (`src/components/os/`) — the portfolio as an early-2000s desktop, booted from the palette, the terminal, the paper plane being swallowed, or visiting `/alejOS`. It renders either on the 3D CRT or in a flat DOM bezel; a boot carrying `{ flat: true }` (the palette's "without the 3D", the terminal's `pc`/`boot flat`, or the `/pc` route) forces the bezel and keeps the whole 3D layer unloaded, while small/touch/reduced-motion devices fall back to it on their own. The desktop is a virtual filesystem (`fs.ts`); apps register in `apps.tsx`/`appWindows.tsx`; `osYear.ts`, `wallpapers.ts` and `sounds.ts` are small subscribable stores. Login/chat/arcade talk to `server/` over one WebSocket.
3. `warp.ts` — the 2D-canvas wormhole between the page and the OS. It opens on the hero wreck's glass (position provided by `BlockName` via `provideWarpOrigin`) and holds until the far side announces its first frame on `OS_SCENE_READY_EVENT`.
4. `CrtScene.tsx` — the presentation shell of the 3D world: renderer, screen glass, camera cinematics, light rig, HUD. The live AlejOS DOM stays interactive on the CRT via a CSS3D renderer sharing the WebGL camera; the glass mesh punches a hole through the canvas with a no-blending near-transparent material. While the camera is parked on the screen **nothing 3D renders at all**. Its `walkTick` is a thin per-frame conductor over the game runtime.
5. `src/game/` — the React-free game runtime (see `src/game/README.md` for the map and the how-to-add-things guide). Input, FPS movement + collision + swimming, the Level system (the 'overworld' and the 'backrooms' easter egg, plus the noclip cut between them), the player body, and the deterministic-procgen core (`core/rand.ts`, `core/textures.ts`).
6. `src/game/world/` — **the open world**: an endless, chunk-streamed procedural planet with Earth-like biomes, water and walkable cities, and `src/game/vehicles/` — **the fleet**: a car, a boat and a helicopter, one per medium. Both are session-scoped detail; the rules that bite live in `src/game/CLAUDE.md`, which loads whenever you work in the runtime, and the long form is `README.md`'s "The open world" and "The fleet" sections.

7. `src/game/net/` + `components/os/worldNet.ts` + `components/os/proximityVoice.ts` — **multiplayer**: the walk is shared. Nothing about the planet travels (it is a pure function of coordinates on both ends), so the wire carries only a roster, a ~15Hz snapshot of everyone's pose, chat, and a WebRTC handshake. The split follows the runtime's rule — the store, the interpolation and the remote bodies are in `src/game/net/` and stay headless-safe; the socket and the voice mesh live on the React side because they reach for `import.meta.env`, a DOM WebSocket and `getUserMedia`. Playback deliberately runs two server ticks behind and interpolates, because extrapolating drags a stopping player's planted feet across the ground. Voice is a peer-to-peer mesh spatialized with `PannerNode`s — **no audio ever touches the VPS**, which is also why there is no TURN relay and some strict-NAT visitors will not connect. `src/game/README.md`'s "Multiplayer" section is the guide.

### Analytics

Traffic is counted by [peeko](https://github.com/aleju03/peeko), my own self-hosted analytics core, wired up in three pieces:

- `src/analytics.ts` — capture. Derives its endpoint from `VITE_CHAT_URL` (so there is no second env var), queues events and posts them in one batch, `sendBeacon` on hide. It subscribes to the `events.ts` spine, so the palette, terminal, chooser, navigation and every route into the OS are instrumented with **no call sites in those components** — add new site-wide instrumentation there first. Explicit `track()` calls exist only where the event has no window event behind it (project opened, contact clicked, app opened, login).
- `server/src/analytics.js` — the store. Capture is a public, origin-checked, rate-limited HTTP route; every **read** is admin-only and travels over the already-authenticated chat WebSocket, so no dashboard token ever reaches a browser. peeko's own `/monitor` and `/live` routes are deliberately not mounted.
- `src/components/os/PeekoApp.tsx` + `peeko.ts` — the dashboard, an AlejOS app that only appears in the admin's Start menu. Hiding it is presentation; the server refusing the reads is the actual gate.

Anything beyond peeko's extracted columns rides in the props bag and is read back with `getBreakdown`, so new custom events need no server change. `src/game/` stays out of this — the runtime must keep running headless, so instrument from the React side (`CrtScene`), never from inside the sim.

### Data is the single source of truth

`src/data/projects.ts` / `experience.ts` / `skills.ts` drive the React pages **and** `/llms.txt`, which a Vite plugin in `vite.config.ts` generates from the same modules so the plain-text rendering can't go stale. Content edits go in the data modules, not components.

## Conventions that matter

- **Nothing shipped, nothing copyrighted**: sounds are synthesized with WebAudio (`sounds.ts`, `game/levels/backrooms.ts`), textures are drawn onto canvases at runtime (`canvasTexture` in `src/game/core/textures.ts`). Keep new assets procedural. Two exceptions, both CC and both credited in a `LICENSE.md` beside the files — additions there must be too: the GLB models in `public/os/models/`, and the three house-door clips in `public/os/sfx/` (`game/core/sfx.ts`, which still keeps a synthesized voice per clip as its cold-load fallback). A recorded one-shot must be peak-matched against the synthesized sounds before it ships; normalized clips run ~4x hotter than this mix. Some of the world's GLSL (the sky's FBM clouds, the water's Voronoi cel highlights, the grass recipe) is adapted from `cortiz2894/stylized-components` (MIT © Christian Ortiz), credited in the module headers where it lives — keep those notices when moving the code.
- **3D performance idioms** (the target is *tiered*: `src/game/world/quality.ts` classifies the GPU before any level builds — discrete cards get a wider grass field, fuller canopies and a 2048 sun shadow map; integrated/mobile/software renderers get the lean tier everything was first tuned on, with CrtScene's adaptive pixel-ratio governor under both. Add new density/budget knobs to the tier record, not as new constants): house shadow maps are hand-baked (`shadow.autoUpdate = false`, flagged with `needsUpdate` only near a moving caster, with the cold one-light-per-frame bake completed under `BootCover`); the sun also keeps `castShadow` and `shadow.autoUpdate = false` stable, fades strength through a uniform indoors/at night, and refreshes its moving map after meaningful travel or solar rotation. Static scene graphs get `matrixAutoUpdate = false` after one `updateMatrixWorld(true)` — anything that must keep moving opts out via `userData.dynamic`; geometry is merged/instanced per chunk; the house-model download overlaps the first shader compile, but attachment and model-dependent compilation finish under `BootCover` so no new variant lands mid-walk. The open world adds two more: chunk building is queued and time-boxed (`streamer.ts`'s `BUDGET_MS`) so a border crossing never costs a frame, and stylized shading is done by `onBeforeCompile` injection into standard materials rather than hand-written shaders — that keeps the scene's fog, tone mapping and lighting instead of reimplementing them. Follow these patterns when touching the scene or the frame loop pays for it.
- **Most of a cold boot is the driver linking shaders, not anything this repo does.** Profiled on a discrete card, the `/room` boot spent ~4.6 s inside three's `WebGLUniforms` — reached from `setProgram → getUniforms → onFirstUse`, which is the *first draw* of a material blocking until its link finishes — and halves on the next load once the browser has the programs cached. Two consequences worth keeping. **Nothing may be left to link mid-walk**: toggling the sun's `castShadow` at the indoor or night threshold changed the shader configuration and used to link every depth-capable surface variant in one frame, measured at 2.8 s. That flag is now invariant, and `warmForRoam` pays the real depth draw during boot at the actual front-door position. The car's two headlights likewise change `NUM_SPOT_LIGHTS` when they appear at dusk, so `setLightWarmup(true)` exposes them at zero intensity for a covered compile and first draw before restoring their live visibility. And **forcing first draws is usually a bad trade** — a four-heading sweep to warm every chunk cost nearly four seconds to avoid a hitch worth a tenth of one. Measure before moving a cost around; `info.programs.length` before and after an action tells you whether a stall is linking or something else.
- **Anything covering a load must animate on the compositor.** `BootCover.tsx` is over a main thread that is blocked in multi-second lumps, so its bar is a `transform: scaleX` transition and its sweep is a `translateX` keyframe. `warp.ts` follows the same rule: canvas draws the entry and exit, but a pre-promoted transform/opacity-only DOM tunnel owns the covered ride while AlejOS and the room load. A rAF loop, a React counter or an animated `width` all freeze solid for exactly the part of the wait they exist to cover.
- **Module-header prose comments**: nearly every nontrivial module opens with a paragraph explaining what it owns and why it's shaped that way (see `game/levels/houseWorld.ts`, `warp.ts`, `CrtScene.tsx`). Keep them accurate when changing behavior, and write one for any new module.
- Walk-mode collision is a flat `THREE.Box3[]` (`game/physics/collision.ts`), height-aware: a box blocks only where it overlaps the body, so a low enough top is a floor you climb (`supportY`) rather than a wall. Solids must register a box or the player walks through them (the backrooms entrance works by deliberately not registering one), **and must be marked `noStand()` unless their box top is somewhere a player could stand** — walls, fences, lamp poles and canopies are taller than the things they wrap, and the climbable furniture below them otherwise chains into a ladder onto the wall tops. Each level owns its CollisionSet; new areas implement the `Level` contract in `game/levels/types.ts`. Ground height is `Level.groundYAt(x, z)` where a level has terrain, and a flat `groundY` where it doesn't; a level with a `waterY` swims when the water is over the chest. The one exception to the box is a solid that *rotates*: an AABB around a 9.4-unit car parked at 45° is 9.5 units wide, and you meet it two units off the paint. Those carry a `hull` — an oriented profile of stations (half-width and standable height per local z, blended linearly) that the box then merely bounds as a broad phase. Only the vehicles have one, and their tables are mapped off the same `SECTIONS` the bodywork is lofted from; everything the world builds is axis-aligned by construction and pays nothing for the feature.
- **The camera's far plane must clear the sky dome's radius outright.** A far plane is a plane; a dome centred on the camera is a sphere, so everything within `acos(far / radius)` of the view axis is clipped. At `far = 400` against a 430 dome that was a hard-edged forty-degree disc of empty background pinned to the middle of the screen, sliding over the stars as you turned — it looks like a texture bug and it is a frustum bug.
- **The game runtime stays React-free and renderer-optional**: `src/game/` must keep running headless — that is what let the multiplayer store and the remote bodies be driven and asserted on in Node, and the long-term plan is still this sim running authoritatively there. React components render and orchestrate; they don't own game state.
